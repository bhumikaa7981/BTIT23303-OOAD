How to read one class

A class diagram gives us a structural view of a system — it shows the classes, their data, their operations, and the relationships between them. Before we connect classes together, let's learn to read just one. Click each part of the box below.

Tap a compartment on the class box to learn what it means.
VisibilitySymbolMeaning
public+Visible to every other class — anyone can call or read it.
private-Visible only inside this class itself.
protected#Visible to this class and any of its subclasses.
package~Visible only to classes in the same package.

Remember: the three compartments are always in this order — name on top, attributes (data / "nouns") in the middle, operations (behaviour / "verbs") at the bottom.

Multiplicity — worked example

Simply put…

"Multiplicity tells us HOW MANY objects can participate in a relationship." Reading left to right: exactly 1 Student is associated with 0..* (zero or many) Courses. Meaning: one student can be enrolled in zero or many courses.

Common multiplicity symbols
SymbolMeaning
1Exactly one
0..1Zero or one (optional)
0..* (or *)Zero or many
1..*One or many (at least one)
3..5Between 3 and 5

Common mistake: writing the multiplicity next to the WRONG class. Remember — the number near a class tells you how many objects of that class participate, from the other side's point of view.

01 · Foundations

What is State Modeling?

State modeling describes the dynamic life of a single object — every state it can be in, and every event that moves it to the next one. Where a class diagram shows structure, a state diagram shows behaviour over time.

Event

The trigger

A noteworthy, instantaneous occurrence that can cause an object to change state — insertCard(), timerExpired, paymentReceived.

State

The condition

An abstraction of an object's attribute values that decides which events matter right now — Idle, Connected, Overdue.

Transition

The move

A directed link between two states: event [guard] / action — fires only when its guard condition is true.

03 · State Diagram Behaviour

What happens inside a state

A state isn't just a label — it can run its own entry, exit and ongoing actions, and even react to an event without actually leaving.

KeywordFires…
entry /exactly once, the instant the state is entered
exit /exactly once, the instant the state is left
do /continuously while the object stays in the state
self-tr.re-runs exit+entry without changing state
Media Player

entry / startBuffer()
do / renderFrames()
exit / releaseCodec()

Smart Door Lock

entry / engageBolt()
do / monitorSensor()
exit / disengageBolt()

Home Alarm

05 · State Generalization

Inherited transitions

A superstate can define one transition that every substate inherits — exactly like a shared method factored into a parent class.

Class Generalization (Unit 1)

About CLASSES

SavingsAccount and CurrentAccount inherit shared attributes/operations from an Account superclass. This is a relationship between two different classes — it shapes the STRUCTURE of the system.

State Generalization (Unit 2)

About STATES, inside ONE class

Authenticating and Authenticated are two states of the SAME object (e.g. one NetworkConnection). A shared transition (like error/disconnect) is factored onto their superstate. This is entirely about the BEHAVIOUR of one class, over time.

Common mistake: assuming "generalization" always means classes. In a state diagram, generalization/inheritance applies to STATES — the object never changes class, it just shares transitions across a family of related states.

06 · Concurrency

Orthogonal regions

Split a composite state into parallel regions and an object can be in more than one substate at once — true concurrency inside a single object.

09b · Scenarios

From use case to one concrete path

"A scenario is one specific path through a use case." A use case like Withdraw Cash covers every possible way that could go; a scenario picks ONE actual sequence of steps — usually the "happy path".

Use Case: ATM — Withdraw Cash

One scenario

  1. Insert card
  2. Validate card
  3. Enter PIN
  4. Validate PIN
  5. Enter amount
  6. Dispense cash

A DIFFERENT scenario of the same use case might branch at step 4: "Validate PIN fails → card retained." Same use case, different path.

15 · Exam-Ready Revision

OOAD Unit 1 + Unit 2 quick revision

A fast, exam-oriented recap — not a question paper, just the notation, rules and typical prompts refreshed in one place.

Class Diagram Notation

  • 3 compartments: Name / Attributes / Operations
  • + public, - private, # protected, ~ package
  • Italic name / «abstract» = abstract class
  • /attr = derived attribute
  • {constraint} = business rule in braces

Relationship Symbols

  • —— plain line = association
  • —▷ hollow triangle = generalization
  • —◇ hollow diamond = aggregation
  • —◆ filled diamond = composition
  • ┄┄▷ dashed = dependency / association class link

Multiplicity Symbols

  • 1 = exactly one
  • 0..1 = zero or one
  • 0..* (or *) = zero or many
  • 1..* = one or many
  • 3..5 = an exact range

State Diagram Notation

  • ● filled circle = initial state
  • ◎ ringed circle = final state
  • rounded box = state (+ entry/do/exit)
  • event [guard] / action = transition label
  • parallel bars inside a box = concurrency

Use Case Notation

  • stick figure = actor
  • oval = use case (verb phrase)
  • rectangle = system boundary
  • «include» = mandatory reuse
  • «extend» = optional add-on

Sequence Notation

  • dashed vertical line = lifeline
  • narrow bar on lifeline = activation
  • solid arrow = synchronous message call
  • dashed arrow = return message
  • small loop = self-message

Activity Notation

  • ● = initial node, ◎ = final node
  • diamond = decision / merge
  • thick bar = fork (split) / join (merge parallel)
  • swimlane = who is responsible

Common Mistakes

  • Confusing aggregation (weak) with composition (strong)
  • Writing multiplicity on the wrong end
  • Treating «extend» as if it were mandatory
  • Storing a derived attribute as a normal one
  • Mixing up Class Generalization with State Generalization

Typical exam-style prompts

Draw a class diagram for a Library Management System. Draw a state diagram for an ATM PIN authentication process. Draw a sequence diagram for Online Checkout. Differentiate between include and extend. Explain aggregation and composition with examples. Differentiate Class Generalization and State Generalization. Draw an activity diagram with a fork/join for Food Delivery. What is an association class? Give an example.
Wrap-up

Key takeaways

Class Modeling
  • Three compartments: name, attributes, operations
  • Multiplicity tells us HOW MANY objects participate
  • Aggregation = weak "has-a"; Composition = strong "has-a"
  • Association classes hold data that belongs to the LINK itself
State Modeling
  • One object, one lifecycle — captured as states and transitions
  • Transitions fire on event [guard] / action
  • Composite states group and generalize shared substate behaviour
  • Orthogonal regions model true concurrency in a single object
Interaction Modeling
  • Use cases capture what the system does, from the actor's view
  • include = mandatory reuse, extend = optional insertion
  • Sequence diagrams show when objects talk, one scenario at a time
  • Activity diagrams with swimlanes show how and who
